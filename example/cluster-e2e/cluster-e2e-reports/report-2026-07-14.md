# 附录:31 路长录制根因追踪与修复(2026-07-14 下午)

31 路并发长录制(30/60min)出现录制碎片化。经三轮单机复测定位为**两层根因**,均已修复并验证。

## 现象与排查

- 流从未掉线(测试窗口 unpublish=0),但录制任务重启 ~350 次;15:49 单分钟 185 次 trailer。
- 排查陷阱:grep 带 ANSI 色码的日志会漏配 `reason=discard`(色码在 = 与值之间),必须先 `sed -E 's/\x1b\[[0-9;]*m//g'`。

## 根因一:sqlite 并发写锁(代码回归,commit `dd2b96ec` 修复)

- `server.go` 对 sqlite 开 100 连接;sqlite 单写者,多连接并发写必然 `database is locked`。
- 上传解耦(U1)使 4 路并发上传的延迟入库并发写 DB,引爆锁争抢;`recoder.go` CreateStream 在**帧回调里同步 INSERT**,等锁 10s(ctx 超时)→ 订阅者被 ring buffer 丢弃(`reason=discard`)→ 无限重试 → 雪崩。
- 修复:sqlite/duckdb 连接池 MaxOpenConns=1;DSN 注入 WAL+busy_timeout(5000)+synchronous(NORMAL);帧路径 DB 超时 10s→2s。

## 根因二:机械盘 IOPS 全局停顿(环境+代码放大,commit `ae298dab` 修复)

- 133 的 /root+/home 同在一块 300G HDD(ROTA=1),MinIO 数据、录制临时文件、日志、DB 共盘。
- `S3File.Write` 每帧一次 write syscall:31 路 ×~50 帧/秒散布在 31 个文件 = HDD 随机写灾难;writeback 风暴时全部录制 goroutine 同时阻塞在 write()(31 路**同一毫秒**收到 ErrDiscard 为铁证)。
- 重试退避上限仅 2s:每次重启产生「新文件+trailer+上传」额外 IO,正反馈放大(trailer 8→16→63→79/分钟)。
- 修复:S3File 顺序写经 1MB bufio 合并(随机访问路径先 flush 保证一致性);录制重试退避上限 2s→30s 作断路器。
